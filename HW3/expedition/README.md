## 1. Условие задачи
Группа роботов исследует клеточную карту с препятствиями, опасными зонами, целями, зарядными
станциями и ретрансляторами. Роботы получают задания, едут к целям, исследуют их и передают данные
на базу. У роботов ограничены энергия, приборы и память. Связь есть только в зонах базы и
ретрансляторов; сообщения задерживаются, теряются и дублируются. Диспетчер распределяет задания и
повторно назначает потерянные после тайм-аута. База, диспетчер, роботы, зарядные станции и
ретрансляторы — самостоятельные участники модели.

## 2. Сценарий: сущности и процессы
Предметная логика взята из ИДЗ №2 без изменений; потоки заменены процессами.

| Участник | Процесс | Поведение |
|---|---|---|
| Часы модели | главный (`main`) | создаёт мир и объекты IPC, начинает такт, ждёт всех участников, проверяет инварианты и завершение, выводит события и карту, удаляет объекты IPC |
| Робот (×N) | `run_part` → `robot_tick` | автомат: к цели, исследование, данные, передача, зарядка, стоянка, авария |
| Диспетчер | `run_part` → `dispatcher_tick` | телеметрия, тайм-ауты, назначение fifo/nearest |
| Узел связи: антенна базы и каждый ретранслятор | `run_part` → `node_tick` | пересылает сообщения своей зоны: задержка, потеря, дублирование |
| Зарядная станция (×M) | `run_part` → `charger_tick` | выдаёт энергию роботам на своих разъёмах из запаса |
| База | `run_part` → `base_proc` | не привязана к тактам: спит на семафоре ящика, засчитывает пакеты по номеру, шлёт подтверждения |

В демонстрационном сценарии 11 процессов-участников (4 робота, диспетчер, 3 узла связи, 2 станции,
база) и часы.

**Три программы из одних исходников** (различаются сборкой и опцией `-R`):

| Оценка | Программа | Запуск участников | Семафоры | Обмен данными |
|---|---|---|---|---|
| 4–5 | `expedition` | часы порождают `fork` | именованные (`sem_open`, имена `/expdPID_k`) | разделяемая память POSIX `/expdPID` |
| 6 | `expedition_u` (`-DUNNAMED`) | часы порождают `fork` | безымянные в разделяемой памяти (`sem_init`, pshared = 1) | та же разделяемая память |
| 7–8 | `expedition -R роль` | каждый процесс запускается своей командой | именованные `/expd_k` | разделяемая память `/expd` |

**Разделяемая память.** Весь мир — одна структура `World` без указателей (карта, роботы, задания,
очереди узлов связи, ящик базы, ГСЧ каждого участника, кольцевой буфер событий). Часы готовят её в
обычной памяти (`world_init`) и копируют в объект `shm_open` + `ftruncate` + `mmap`. Независимый
участник подключается `shm_open` + `mmap`; параметры сценария ему не нужны — всё уже в памяти.

**Семафоры** (`ipc.c`, остальной код обращается к ним по номеру):

| Семафор | Начальное значение | Зачем |
|---|---|---|
| `S_MX` | 1 | двоичный семафор вместо мьютекса: шаг такта каждого участника и обработка пакета базой — критические секции; двое роботов не встанут в одну клетку |
| `S_GO + i` | 0 | часы разрешают участнику i выполнить такт |
| `S_DONE` | 0 | участник закончил такт (часы ждут N раз) или завершил процесс |
| `S_INBOX` | 0 | пакеты в ящике базы: производители — узлы связи, потребитель — база |
| `S_SLOT + c` | `charger_slots` | свободные разъёмы станции c: робот занимает `sem_trywait`, освобождает `sem_post`; разъёмов нет — «очередь к станции» |
| `S_JOIN` | 0 | независимый участник подключился (часы ждут всех) |

Захват один (`S_MX`), поэтому взаимоблокировок нет; робот не ждёт разъём блокирующим вызовом —
иначе остановились бы часы. Порядок участников внутри такта задаёт планировщик ОС, поэтому при
одном seed прогоны различаются (seed фиксирует решения каждого участника, но не порядок процессов).

**События.** `ev()` в любом процессе под `S_MX` пишет строку в кольцевой буфер в разделяемой
памяти (512 строк); часы после каждого такта выводят новые строки на экран и в журнал — вывод
процессов не перемешивается. Независимый участник дополнительно печатает свои события в свой
терминал.

## 3. Интерфейс
- Обычный режим — поток событий по строке на событие: `[такт] ВИД текст`. В начале — строка о
  каждом процессе: `ПРОЦЕСС  pid 1234: робот R1`.
- `-m` — каждый такт перерисовывается экран: карта (роботы — цифры, X — авария, выполненные
  цели — заглавные буквы), состояние роботов, сводка, последние события.
- `-v` — дополнительно каждый шаг, такт зарядки и исследования, пересылки узлов.
- Журнал `expedition.log` (`open`/`dprintf`, ведут часы) содержит все события и итоговый отчёт.
- Параметры: встроенный сценарий, файл сценария `-c` (формат — в начале `config.c` и в
  `tests/*.cfg`), опции командной строки (`./expedition -h`).

## 4. Запуск и завершение

```bash
make
```

```bash
./expedition -m
```

```bash
./expedition -c tests/t9_queue.cfg -s 5
```

Безымянные семафоры (только Linux: в macOS `sem_init` для процессов не поддерживается):

```bash
make expedition_u && ./expedition_u -m
```

Независимые процессы — часы и каждый участник в своём терминале. Часы печатают команды для всех
участников сценария и ждут, пока подключатся все:

```bash
./expedition -R clock -m
```

```bash
./expedition -R robot:1
```

То же одной командой — скрипт запускает часы и всех участников (`-R list` выдаёт роли сценария):

```bash
./run_separate.sh -c tests/t1_ideal.cfg
```

```bash
./expedition -t 0
```

`-t 0` — без ограничения тактов, выход по Ctrl+C. Обработчик SIGINT/SIGTERM в любом процессе
ставит `signo` в разделяемой памяти и больше ничего не делает; участники продолжают такты, часы
в начале следующего такта завершают модель: поднимают `stop`, будят всех (`S_GO`, `M_STOP` базе),
ждут `S_DONE` от каждого процесса (детей — ещё и `waitpid`), печатают итоги и удаляют семафоры
(`sem_unlink` / `sem_destroy`) и память (`shm_unlink`). Поэтому Ctrl+C у часов, у всей группы
процессов или у любого независимого участника дают одинаковый результат — код 4. SIGPIPE часы
игнорируют (вывод в `| head` не обрывает модель).

| Код | Причина |
|---|---|
| 0 | выполнены все доступные задания |
| 1 | ошибка в параметрах или сценарии; участник не нашёл мир или роль занята |
| 2 | достигнут предел тактов |
| 3 | ресурсы исчерпаны: нет исправных совместимых роботов, кончилась энергия станций или нет прогресса |
| 4 | прервано сигналом SIGINT или SIGTERM, итоги сохранены |
| 5 | нарушен инвариант |

## 5. Результаты
- Демонстрационный сценарий (seed 7), все три программы: 8 из 9 заданий выполнены за 103–106
  тактов (число зависит от порядка процессов), 'k' недоступно — нет магнитометра. Были потери и
  дубликаты в узлах связи, 3 повторные передачи, одно назначение потеряно и выдано повторно;
  база засчитала 18 уникальных пакетов и отбросила 3 дубликата. Инварианты не нарушены.
- 30 прогонов демо с разными seed (fork, macOS): 27–28 — код 0, 2–3 — код 3 (в опасной зоне
  разбился R1 — единственный робот со спектрометром, задания 'b' и 'g' невыполнимы — законное
  исчерпание ресурсов).
- Во время работы в Linux в `/dev/shm` 40 объектов у `expedition` (память + 39 семафоров
  `sem.expd…`) и 1 у `expedition_u` (семафоры внутри памяти); после завершения — 0, в том числе
  после Ctrl+C.
- `make test` в macOS: 14 из 14 проверок. В Linux (Docker, gcc 16.2) обе сборки — без
  предупреждений, `make test` — 15 из 15 для `expedition` и 15 из 15 для `expedition_u`.
  Проверки: t1–t9 из ИДЗ №2 (коды и ключевые события; авария — серией из 10 seed), SIGINT часам,
  SIGINT всей группе процессов, независимый запуск (код 0), SIGINT одному независимому роботу
  (код 4), не осталось процессов, в Linux — не осталось объектов в `/dev/shm`.
- Проверку воспроизводимости журнала (была в ИДЗ №1) не переносил: порядок процессов внутри такта
  недетерминирован, журналы двух прогонов с одним seed различаются.

## 6. Использование ИИ и критическая оценка
Код создан с помощью ИИ по промтам из [PROMPTS.md](PROMPTS.md): шаг 0 — контекст, дальше шаги по
модулям. После каждого шага программа собиралась и проверялась; найденные ошибки оформлены
отдельными промтами под шагами.

Исправления:
1. **Часы погибли от SIGPIPE, участники зависли** ([шаг 3.1](PROMPTS.md)). После
   `./expedition | head` в системе остались 11 процессов и все объекты IPC: часы умерли при записи
   в закрытый канал, а участники вечно ждали семафор такта. Часы теперь игнорируют SIGPIPE.
   Ошибка найдена ручной проверкой; ИИ её не предусмотрел, хотя сам писал удаление объектов «при
   любом завершении».
2. **Род в событиях** (там же): «база запущен», «станция C1 запущен» → «ПРОЦЕСС  pid N: база».
3. **Обрезанная строка СТАРТ** ([шаг 5.1](PROMPTS.md)): буфер события считался в символах, а
   русская буква занимает 2 байта — `EVLEN` увеличен до 256. Убраны дублирующие строки ожидания.

Ограничения:
- Если часы убить SIGKILL, участники останутся ждать на семафоре, а объекты IPC — в системе.
  Независимые часы при следующем запуске сами удаляют старые объекты `/expd*`; объекты версии с
  fork (имя содержит pid) удаляются вручную (`rm /dev/shm/*expd*` в Linux).
- Независимый запуск — одна модель одновременно (постоянное имя `/expd`). Участники должны быть той
  же сборки, что и часы.
- В macOS работают только именованные семафоры; `expedition_u` собирается там с предупреждением
  `deprecated` и при запуске сообщает, что нужен Linux. Проверка варианта 6 — в Docker.
- Создаются все 39 семафоров независимо от числа участников сценария — так проще код, лишние не
  используются.
