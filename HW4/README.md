## 1. Условие

Роботы исследуют цели на клеточной карте с препятствиями, опасными зонами, базой,
зарядными станциями и ретрансляторами. Диспетчер назначает цели с учётом приборов
и ресурсов роботов. Роботы едут к цели, измеряют, хранят данные в памяти и передают
их из зоны связи. Канал задерживает, теряет и дублирует сообщения. Диспетчер может
повторно выдать потерянное задание после тайм-аута. База засчитывает номер пакета
один раз и отмечает цель выполненной после получения всех фрагментов.

## 2. Участники и обмен по TCP

| Участник | Где выполняется | Действие |
| --- | --- | --- |
| Часы и карта | Процесс `server` | Хранит мир, ведёт такты, принимает шаги роботов, проверяет инварианты и условия завершения |
| Диспетчер | `dispatcher_tick` на сервере | Обрабатывает телеметрию и тайм-ауты, назначает задания по FIFO или ближайшей цели |
| Антенна базы и ретрансляторы | `node_tick` на сервере для каждого узла | Доставляют модельные сообщения с учётом задержки, потери и дублирования |
| База | `base_tick` на сервере | Разбирает ящик, учитывает уникальные пакеты, отправляет подтверждения |
| Зарядные станции | `charger_tick` на сервере для каждой станции | Выдают энергию из запаса, число занятых разъёмов следует из состояний роботов |
| Робот | Один процесс `robot` на номер | Выполняет `robot_tick`, возвращает состояние робота, попытки передачи и события |
| Наблюдатель | Отдельный процесс `watch` | Показывает общие события, карту и итог экспедиции |
| Управление | Одноразовый процесс `control` | Отключает робота и запрещает или разрешает его следующий вход |

Сервер ждёт, пока каждый робот подключится хотя бы раз. В такте диспетчер выдаёт
задания, узлы связи пересылают сообщения, база разбирает ящик, затем роботы
выполняют по шагу и станции пополняют заряд. Первый робот в очереди меняется
с каждым тактом. Сервер проверяет совместимость заданий, запас энергии, занятость
клеток и разъёмов, учёт пакетов и полноту данных по выполненным целям.

При подключении робот получает конфигурацию карты и строит поля расстояний.
В каждом такте сервер отправляет ему изменяемые данные, нужные для шага. Сервер
применяет только полный ответ от нужного соединения и для ожидаемого такта.
Во время ожидания работает `poll`, поэтому сервер продолжает обслуживать
остальные соединения. Кадр состоит из типа и длины тела в сетевом порядке и тела
до 16 КиБ. Конфигурация, снимок и результат шага передаются в представлении
структур C, поэтому серверу и роботам нужна одинаковая версия программы и
совместимое представление типов. Модельные задержки, потери и дубликаты
генерируют узлы связи внутри модели поверх надёжного TCP.

Если робот отключился или не ответил за 2 секунды, сервер сохраняет последний
принятый результат, пропускает его следующие шаги и освобождает разъём, если
робот заряжался. При повторном входе работа продолжается с сохранёнными
координатами, зарядом и данными. Если отключились все роботы, часы ждут
возвращения хотя бы одного, а сервер продолжает принимать соединения.

## 3. Интерфейс

Сервер показывает подключения, отключения, команды управления и завершение.
Робот показывает свои события. Наблюдатель получает снимок экспедиции при
подключении и поток общих событий после него. С `-m` он отображает карту,
состояния роботов, станции, сводку и последние события на каждом такте.
До восьми наблюдателей могут подключаться, уходить и подключаться повторно
в любой момент. При переполнении очереди медленного наблюдателя сервер
отключает это соединение.

По умолчанию сервер сохраняет полный журнал и итоги в `expedition.log`.
У наблюдателя итоги отображаются в терминале. Сервер принимает файл сценария
`-c`, seed `-s`, стратегию `-S fifo|nearest`, предел тактов `-t`, задержку `-d`
в миллисекундах и путь к журналу `-l` (`none` отключает запись). Ключ `-v` у
робота и наблюдателя включает подробные события, у сервера — приём каждого
шага. Формат сценария показан в файлах [tests](expedition/tests).

## 4. Запуск и завершение

Из каталога `HW4` соберите проект и запустите встроенный сценарий. `make run`
запускает на `127.0.0.1:5054` сервер, четырёх роботов и наблюдателя с картой.

```bash
cd expedition
make
make run
```

Для раздельного запуска из каталога `expedition` откройте сервер. В этом примере
сценарий содержит двух роботов.

```bash
./expedition server 0.0.0.0 5054 -c tests/t1_ideal.cfg -d 250
```

В других терминалах или на других машинах запустите по одной команде на
процесс. Замените `192.168.1.10` на IPv4-адрес сервера. Для запуска на одном
компьютере используйте `127.0.0.1` и в команде сервера, и в командах клиентов.

```bash
./expedition watch 192.168.1.10 5054 -m
```

```bash
./expedition robot 192.168.1.10 5054 1
```

```bash
./expedition robot 192.168.1.10 5054 2
```

Чтобы отключить R1, затем разрешить ему вернуться, выполните эти команды во
время прогона. Последняя команда заново запускает рабочий клиент.

```bash
./expedition control 192.168.1.10 5054 off 1
./expedition control 192.168.1.10 5054 on 1
./expedition robot 192.168.1.10 5054 1
```

Получив SIGINT или SIGTERM, сервер записывает итоги, передаёт наблюдателям
отчёт и всем подключённым клиентам итоговый код, затем закрывает сокеты.
Ctrl+C у отдельного клиента отключает только его. `-t 0` снимает предел
тактов. Успешная команда управления и рабочий клиент, завершённый командой
`off`, возвращают 0. Роботы и наблюдатели, получившие итог, возвращают код
сервера.

| Код | Причина завершения |
| --- | --- |
| 0 | Выполнены все доступные задания |
| 1 | Ошибка параметров, сценария или соединения |
| 2 | Достигнут предел тактов |
| 3 | Ресурсы исчерпаны или модель перестала продвигаться |
| 4 | Получен SIGINT или SIGTERM |
| 5 | Нарушен инвариант |

## 5. Результаты

```bash
make test
```

- Встроенный сценарий, seed 7. Выполнены 8 из 9 заданий за 100 тактов. Цель
  `k` недоступна, так как у роботов нет магнитометра. База засчитала 18
  уникальных пакетов и отбросила 3 дубликата. Канал потерял 1 назначение,
  4 пакета данных и 1 подтверждение. Все 100 проверок инвариантов прошли.
- `make test` на macOS arm64 и Linux aarch64 (Docker, GCC 16.2.0) — **11 из 11**
  на каждой системе, сборки без предупреждений. В 7 из 10 прогонов сценария
  `t7_failure` наблюдались авария и повторное назначение с успешным итогом.
  При SIGINT сервер, два робота и наблюдатель вернули код 4. В тесте
  переподключения один наблюдатель и робот вернулись после SIGINT, вход R1
  между `off` и `on` был отклонён, последующий запуск R1 и выполнение
  сценария завершились кодом 0.
- В разных контейнерах Docker сервер работал по адресу `172.19.0.2`, два
  робота и наблюдатель — по адресу `172.19.0.3`. Сценарий `t1_ideal` завершился
  за 36 тактов без нарушений инвариантов. Все четыре процесса вернули код 0.
- В ручной проверке одновременно работали восемь наблюдателей. Сервер
  отклонил девятого и принял нового после освобождения места. После
  отключения обоих роботов номер такта остался равным 2, с возвратом R1
  такты возобновились. Все восемь наблюдателей получили итоги при SIGINT серверу.

Порядок вычислений внутри такта задан на сервере, а момент подключения и
отключения зависит от сети и планировщика. Поэтому тесты проверяют коды и
характерные строки, а точное совпадение журналов двух прогонов не проверяется.

## 6. Использование ИИ и критическая оценка

ИИ помог перенести код ДЗ3, реализовать протокол и подготовить тесты.
Работа велась по шагам из [PROMPTS.md](expedition/PROMPTS.md). После каждого шага
проводилась проверка. По её результатам исправлены следующие ошибки.

1. Временная проверка использовала `INADDR_LOOPBACK`, недоступный в выбранном
   режиме заголовков macOS. Заменил его на `inet_pton`.
   [Промт 1.1](expedition/PROMPTS.md#11-исправление-адрес-loopback-в-проверочном-коде)
2. В проверке отказа порт оставался занят сокетом без `listen`. На macOS это
   вызвало тайм-аут. После освобождения порта проверка получила `ECONNREFUSED`.
   [Промт 1.2](expedition/PROMPTS.md#12-исправление-проверка-отказа-в-подключении)
3. Имя кадра `F_OK` совпало с макросом из `unistd.h`. Переименовал кадр в
   `F_CONTROL_OK`.
   [Промт 4.1](expedition/PROMPTS.md#41-исправление-имя-кадра-подтверждения)
4. Временная проверка паузы сравнивала весь вывод карты. При уходе робота карта
   получила обновление с тем же тактом. Проверка теперь сравнивает номер такта.
   [Промт 5.1](expedition/PROMPTS.md#51-исправление-проверка-паузы-с-восемью-наблюдателями)

Сервер хранит состояние в памяти до завершения процесса. Протокол рассчитан
на учебную доверенную IPv4-сеть, команды управления доступны любому клиенту
с доступом к порту. Один такт включает последовательные обмены с роботами,
поэтому его длительность зависит от сетевой задержки.
